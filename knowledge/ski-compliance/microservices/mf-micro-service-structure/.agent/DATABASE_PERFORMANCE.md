## 1. Indexing Principles for Marketing Structure Data

- **Composite Key Left-Prefix**:
  - Most queries on `marketing_structures` filter by `period` and one or more additional columns (`code`, `division_id`, `user_id`, `office_id`).
  - Index definitions must place high-selectivity or equality filter columns first: `(period, code)`, `(period, division_id)`, `(period, marketing_position_id)`.
- **Avoid Overlapping Indexes**:
  - An index on `(period, code)` already covers queries filtering solely by `period`.
- **Soft-Delete Considerations**:
  - Queries filtering active records include `deleted_at IS NULL`. Where applicable, composite indexes should account for soft-delete filtering.

---

## 2. Query Optimization Guidelines

1. **Avoid `SELECT *` on Wide Views**:
   - For listing endpoints where only basic IDs and names are needed, select specific columns instead of scanning the full hierarchy views.
2. **Prevent N+1 Database Calls**:
   - In batch operations like `CreateDuplicate`, batch insert copied records rather than issuing single `Create` calls in loops.
3. **Analyze Multi-Level Views with `EXPLAIN`**:
   - When tuning `view_marketing_structure_all_levels`, run `EXPLAIN` to confirm MySQL uses indexes for all left joins on `(period, level, id_boss)`.
   - Ensure the query includes `WHERE lv1.period = ?` so the optimizer prunes unrelated historical periods.

---

## 3. Execution Plan Requirements Before Claiming Optimization

Before claiming an optimization:
1. Capture the exact SQL statement generated by GORM.
2. Run `EXPLAIN` on a representative MySQL instance:
   - Check `type` (target `ref`, `range`, or `const`; avoid `ALL`).
   - Check `rows` examined vs returned.
   - Check `Extra` (avoid `Using temporary; Using filesort` on large tables).
3. Report before/after latency and rows examined.
